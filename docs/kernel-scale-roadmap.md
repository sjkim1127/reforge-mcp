# Reforge-MCP: 시스템/커널 이전 프로파일

2026-10-12 시스템 대상 설계. 최상위 제품 정의는 [프로그램·생태계 이전 설계](ecosystem-migration-design.md)를 따른다. Linux는 대표 검증 대상 중 하나이며 제품의 규모 상한이나 유일한 목표가 아니다. 이 문서는 목표 아키텍처이며 커널 포팅 지원을 구현했다는 선언이 아니다.

## 최종 목표

Linux 커널 규모의 C 시스템 소프트웨어를 분석·계획·변환·빌드·실행 검증·수정하는 자동 포팅 시스템을 만든다. Linux를 대표 검증 대상으로 사용한다. 선택한 커밋, 아키텍처, 설정과 워크로드에서 원본 시스템의 인터페이스와 동작을 유지하는 Rust 구현을 산출하는 것이 목표다.

이 프로파일은 C 시스템 소프트웨어를 다룬다. 다른 언어/프레임워크와 더 큰 시스템도 공통 캠페인/의존성 모델에서 별도의 빌드·실행 프로파일로 다룬다. 현재 int32 함수 생성기는 실행/검증 파이프라인을 확인하는 초기 백엔드다. 기존 함수 fixture와 musl abs 결과를 커널 준비도나 전체 프로젝트 포팅 증거로 사용하지 않는다. 커널 전체의 완전 자동 변환과 모든 동작의 동등성은 아직 달성되지 않은 장기 연구·제품 목표다.

## 산출물과 성공의 의미

최종 산출물은 타깃 환경에서 빌드·부팅·시험할 수 있는 Rust 시스템, 재현 가능한 빌드/설정 묶음, 원본과 Rust의 대응표, 검증 기록, 잔여 C/assembly 의존성과 미지원 목록이다. 사용자가 선택한 Linux 대상을 포팅할 때는 사용자 공간 ABI 및 관련 인터페이스 계약을 명시적으로 보존한다. 의미를 개선하거나 취약한 원본 동작을 변경하는 작업은 호환 포팅과 별도 변경으로 기록한다.

자동화 목표는 에이전트가 작업 분해·컨텍스트 조회·후보 생성·오류 진단·수정·검증·재개를 수행하는 것이다. 근거가 부족한 소유권/동시성 결정을 통과시키거나 실패한 검증을 숨기는 것은 자동화 성공이 아니다. 미지원은 계획의 잔여 작업으로 저장한다.

## 아키텍처를 지배하는 조건

| 조건 | 필요한 제품 구조 |
|---|---|
| Kbuild/Kconfig와 생성 헤더 | 실제 빌드에서 얻은 컴파일 명령, `.config`, 생성 파일 및 도구 버전을 스냅샷으로 관리 |
| 같은 파일의 여러 설정/타깃 | 포팅 단위의 ID에 커밋·설정·타깃·컴파일 컨텍스트를 포함; 비활성 코드와 미검증 설정을 별도로 기록 |
| 규모와 반복 작업 | 프로젝트→설정→서브시스템→translation unit→포팅 단위 계층, 디스크 기반 그래프, 증분 분석 및 영향 범위 무효화 |
| 포인터/별칭/자원 수명 | AST 외에 타입, 메모리 효과, 소유권 후보, 할당·해제·참조 카운트 계약을 공통 모델로 저장 |
| ABI/자료 배치 | 타깃별 크기·정렬·오프셋·호출 규약·심볼·bitfield/union을 검증; C 상호운용 경계 유지 |
| 인터럽트/락/원자성/RCU | 실행 컨텍스트, 잠금 순서, 메모리 순서, 수명과 해제 조건을 명시적으로 분석/검증 |
| MMIO/DMA/assembly | volatile·장벽·장치 메모리·inline asm의 효과를 모델링; 미지원 경계는 원본 보존 및 누락 기록 |
| 커널 런타임 | `no_std`, 커널 할당/오류 처리/빌드 시스템을 위한 별도 출력 및 실행 어댑터 |

Clang은 실제 컴파일 컨텍스트의 구문/타입/배치 근거를 제공하는 프런트엔드로 둔다. Joern/CPG는 프로젝트와 서브시스템의 호출·흐름 탐색을 보조하는 어댑터로 둔다. 소유권이나 동시성 계약의 정확성을 그래프 존재만으로 보장하지 않는다. LLM은 제한된 단위의 후보와 수정안을 생성하며, 전체 커널을 한 프롬프트로 변환하는 방식에 의존하지 않는다.

현재 C int32 생성기의 `checked_*`와 panic 처리를 커널의 정수/오류 처리 규칙으로 일반화하지 않는다. 실제 컴파일 옵션, unsigned/wrapping 동작, errno, 할당 실패 및 실행 컨텍스트가 변환 규칙을 결정해야 한다. 현재 standalone Cargo 빌드와 stdout 비교 역시 별도의 초기 프로파일로 남긴다.

## 단계적 이전과 최종 Rust 목표

초기 시스템 이전은 C/Rust 혼합 상태에서 수행한다. 작은 라이브러리/leaf 기능과 드라이버를 시작점으로 삼고, 의존성 및 안전한 추상화가 마련된 서브시스템으로 확장한다. 이 순서는 검증 가능한 경계를 확보하기 위한 개발 방식이며 프로그램·생태계 전체 이전 목표를 축소하지 않는다.

C ABI와 raw pointer를 사용하는 동작 보존 단계와, 검증된 계약을 바탕으로 안전한 Rust 추상화를 만드는 단계를 구분한다. `unsafe` 사용에는 원본 위치, 필요한 조건, 수명/별칭/동시성 불변식과 검증 근거를 기록한다. 아직 C에 위임하는 바인딩만 생성한 단위를 Rust 구현 완료로 집계하지 않는다. 장기적으로 잔여 C 구현을 줄이되 architecture assembly, 장치/펌웨어 경계 등 유지할 경계의 계약을 따로 명시한다.

Linux의 공식 설계는 `no_std`, C bindings와 안전한 abstractions, Kconfig에 따른 conditional compilation을 설명한다. 이 기준에 맞춰 커널 전용 출력 어댑터를 설계한다. [Linux Rust general information](https://docs.kernel.org/rust/general-information.html)

## 검증 경로

| 게이트 | 증거 | 통과가 의미하는 범위 |
|---|---|---|
| 분석 | 빌드 명령/헤더/타입/호출 커버리지, 미해결 항목 | 해당 컨텍스트의 분석 근거 확보 |
| 컴파일/링크 | 원본과 Rust 타깃 빌드, 심볼·배치·ABI 비교 | 해당 설정의 빌드/상호운용 가능 |
| 단위 동작 | 호스트에서 가능한 차등 테스트, KUnit | 명시된 단위/입력/환경에서의 동작 근거 |
| 통합 | QEMU 등 고정 환경에서 빌드 및 부팅, kselftest | 해당 가상 타깃과 설정/워크로드의 실행 근거 |
| 시스템 성질 | 설정에 따른 메모리/락/레이스 검사, fault injection와 fuzzing | 선택된 검사와 워크로드가 다룬 결함 범위 |
| 성능/장치 | 같은 환경의 원본 대비 성능·메모리 측정, 필요한 실제 장치 시험 | 해당 환경과 장치의 비기능 계약 |

각 게이트는 커밋, 설정, 타깃, 도구, 생성 후보, 테스트 및 환경에 묶인다. 부팅 성공을 전체 동등성으로 확대하지 않는다. QEMU 결과를 실제 하드웨어·DMA·타이밍 검증으로 확대하지 않는다. 한 설정의 통과를 다른 Kconfig/아키텍처의 통과로 확대하지 않는다. KUnit과 kselftest는 각각 커널 단위 검사와 selftest의 근거로 사용한다. [KUnit](https://docs.kernel.org/dev-tools/kunit/index.html), [kselftest](https://docs.kernel.org/dev-tools/kselftest.html)

## 다음 구현의 우선순위와 인수 기준

1. **실제 빌드 컨텍스트 수집**: compilation database와 Kbuild 산출물에서 argv/cwd/소스/타깃/설정/생성 헤더를 수집한다. 설정이 다른 동일 파일은 별도 단위다. GNU C 옵션을 기존 `-std=c11` 고정값으로 덮어쓰지 않는다. 선택한 커널 커밋/설정에서 얻은 실제 translation unit을 동일 컨텍스트로 분석하고, 미지원 옵션은 보고한다.
2. **포팅 모델 분리**: 현재 `Function.rust`에 결합된 분석과 생성 구조를 typed IR 및 생성 백엔드로 분리한다. structs/enums/unions, 정수 폭/부호, 포인터, 배열, 함수 포인터, 메모리 효과와 출처를 표현한다. 표현하지 못하는 의미를 생성 단계에서 임의로 메우지 않는다.
3. **혼합 빌드와 ABI**: standalone Cargo와 별개로 커널 Kbuild 출력 어댑터를 만든다. 작은 실제 단위의 C 호출자와 Rust 구현을 함께 빌드하고 타입 배치/심볼 계약을 확인한다. bindings 생성과 원본 함수 구현 이전을 별도 결과로 기록한다.
4. **커널 실행 worker**: 소스/설정/툴체인/커널/루트 파일시스템을 고정한 Linux worker에서 대상 커널을 빌드·부팅·시험한다. 현재 macOS 호스트의 함수 테스트를 커널 실행 검사로 대체하지 않는다. `rustavailable`로 선택한 커널/툴체인의 Rust 빌드 조건을 확인한다. [Kernel Rust quick start](https://docs.kernel.org/rust/quick-start.html)
5. **자동 이전/수정 반복**: 서브시스템 단위 작업 그래프, 생성/검증/수정, checkpoint, 예산과 설정별 재개를 연결한다. 의존 단위의 변경은 관련 설정과 검증 근거를 무효화한다. 이후 실제 드라이버/서브시스템 corpus와 아키텍처/설정 행렬을 확장한다.

첫 번째 다음 마일스톤은 **커널 빌드 컨텍스트를 수집하고 설정/타깃별 분석 단위를 재현하는 것**이다. 커널용 포인터 코드를 변환했다는 주장이나 커널 부팅 성공은 이 마일스톤의 완료 조건에 포함되지 않는다.

## 진행률

계획된 단위/설정/워크로드를 분모로 고정하고 다음을 함께 보고한다.

- 분석 성공/실패/미지원 단위와 미해결 간접 호출.
- C에 위임하는 경계와 실제 Rust 구현으로 이전한 단위.
- 검증된 설정·아키텍처 및 아직 검증하지 않은 조합.
- 최신 후보에 대한 게이트 통과/실패/미실행 상태.
- unsafe 계약과 미해결 소유권/동시성 항목.
- 원본 대비 성능·메모리·생성/검증 비용.

Rust 출력 LOC, 바인딩 개수, 작은 함수 테스트 통과만으로 커널 포팅 완료율을 계산하지 않는다.
