# Reforge-MCP: Agent용 프로그램·생태계 Rust 이전 플랫폼

2026-10-12 제품 정의. 이 문서는 목표 아키텍처이며 아래 기능 전체가 현재 구현됐다는 의미가 아니다.

## 목표

C, C++, Java, Python, Go로 작성된 프로그램, 라이브러리, 프레임워크와 그 의존 생태계를 Rust로 자동 이전하는 Agent용 MCP 인프라를 만든다. Linux 커널은 시스템 프로파일의 대표 검증 대상이고, Ghidra는 복합 애플리케이션 프로파일, Spring Boot는 프레임워크 및 서버 애플리케이션 프로파일의 대표 검증 대상이다. 커널 규모를 제품의 상한이나 유일한 영역으로 두지 않는다.

프로그램 및 여러 프로젝트로 구성된 의존 그래프의 크기를 하나의 프롬프트/메모리 작업에 맞추지 않는다. 캠페인→프로젝트/의존 프로젝트→모듈→분석/변환 단위 계층, 디스크 기반 그래프, 페이지 단위 MCP 조회, 증분 분석, 분산 실행 worker와 checkpoint로 처리한다. 자원/시도 예산은 개별 작업에 적용하며 미실행 단위를 전체 성공으로 집계하지 않는다. 현 엔진의 32파일/256 KiB 제한은 초기 scalar-C 백엔드의 한도이고, 큰 프로젝트 지원을 선언하기 위해 단순히 그 제한만 해제하지 않는다.

최종 목표는 원본의 명시된 인터페이스, 기능, 데이터 형식, 오류 처리 및 실행 계약을 유지하는 Rust 산출물이다. 모든 임의 프로그램의 완전 자동 포팅은 아직 달성되지 않은 제품·연구 목표다. 현재 실행 가능한 구현은 README에 적힌 제한된 C 백엔드다.

## 기계적 변환과 의존 생태계 이전

기계적 변환은 원본 코드를 실제 빌드 컨텍스트에서 읽어 타입/제어 흐름/상태/메모리/실행 모델을 Rust로 옮기는 경로다. 원본 AST에서 문자열 치환을 하거나 다른 crate 이름만 넣는 것을 이식 완료로 보지 않는다. 구현을 보존하는 단계를 먼저 만들고, 검증된 불변식이 있는 부분을 안전한 Rust 및 더 관용적인 API로 개선한다.

외부 의존성은 별도 이전 작업이다. Agent가 원본 라이브러리의 **실제 사용 API와 필요한 동작 계약**을 수집하고 Rust 후보를 찾는다. 후보는 특정 버전과 저장소/문서/라이선스/사용한 API에 묶는다. 같은 분야의 라이브러리라는 사실과 계약을 만족한다는 사실을 구분한다.

| 선택 | 조건 및 산출물 |
|---|---|
| 직접 대체 | 사용된 계약이 후보의 API/동작으로 충족되고 시험을 통과함 |
| 어댑터 작성 | 오류·타입·데이터·호출 방식 등의 차이를 wrapper로 보완하고 시험 |
| 여러 Rust 라이브러리 조합 | 기능을 분할해 조합하고 통합 동작·자원 수명을 시험 |
| 의존 라이브러리 자체 포팅 | 적절한 후보가 없거나 의미 차이가 크면 하위 이전 프로젝트 생성 |
| 임시 FFI/런타임 연결 | 원본 의존성을 명시적으로 남겨 점진적 이전; Rust 구현 완료와 따로 집계 |
| 미지원/추가 조사 | 후보/검증/실행 근거가 부족하면 잔여 작업으로 저장 |

동일 기능의 Rust 라이브러리가 있다고 가정하지 않는다. Agent가 검색 결과만으로 의존성을 확정하지 않는다. 실패/누락/행동 차이는 어댑터·재구현·원본 의존성 포팅 작업으로 이어져야 한다. 대체 라이브러리를 Cargo.toml에 등록한 것만으로 해결 상태를 전이시키지 않는다.

## 의존성 요구사항과 후보 계약

의존성 티켓은 원본 라이브러리 이름만 갖는 항목이 아니다. 최소한 다음 정보를 저장한다.

- 원본 생태계/패키지/버전/빌드 조건과 사용한 API의 출처.
- 동적으로 사용될 가능성이 있는 API, 설정/플러그인/리플렉션 등 분석 누락.
- 입출력·오류·자료 형식·부작용·자원 수명·동시성·성능·배포 계약.
- 후보의 버전, 저장소/문서 근거, 제공 기능과 누락 기능, API 대응과 어댑터 작업.
- 라이선스/플랫폼/타깃/런타임 제약과 유지보수 상태의 조사 시점.
- 계약별 테스트/실행 결과, 후보와 테스트 해시, 미실행/실패 항목.

후보는 `proposed → evaluated → implementing_adapter → verifying → accepted` 상태를 가진다. `rejected`, `blocked`, `stale`도 기록한다. `accepted`는 최신 버전/후보/원본 사용 범위에서 필수 계약의 실행 근거가 통과했을 때만 가능하다. Agent의 설명이나 검색 근거는 실행 검증 결과를 대신하지 않는다. 재검증이 필요한 버전/설정 변경과 영향받는 호출자를 추적한다.

[Agent가 소비할 의존성 티켓 예시](contracts/dependency-resolution.example.json)는 아직 서버의 실행 계약이 아닌 설계 예시다.

## Agent와 서버의 역할

서버는 원본 인벤토리, 빌드/분석 근거, 작업 그래프, 컨텍스트와 계약, 생성 후보, 실행 환경, 검증 결과 및 재개 상태를 제공한다. Agent는 후보 검색/소스 조사, 변환 계획, 어댑터/새 구현 작성, 실패 진단과 수정을 수행한다. 검색은 연결된 registry/source/doc 도구를 이용하거나 후속 서버 어댑터로 지원한다. Agent의 검색 접근을 서버 내부 LLM/네트워크 기능이 이미 있는 것으로 표시하지 않는다.

```text
프로젝트·빌드·의존성 인벤토리
  → 기계적 변환 단위 + 의존성 이전 티켓
  → Agent: Rust 후보 조사 / 어댑터 / 의존 프로젝트 포팅
  → 빌드·계약 테스트·통합 실행
  → 구조화된 실패와 영향 범위 → Agent 수정
  → 검증된 산출물 + 원본 대응표 + 잔여 의존성과 한계
```

계획된 MCP 계약은 `inventory_project`, `get_dependency_requirements`, `record_dependency_candidate`, `plan_dependency_adapter`, `verify_dependency_replacement`, `next_migration_tasks`다. 이 도구들은 아직 구현되지 않았다. 기존 `generate_rust`, `submit_rust_candidate`, `verify_port`는 현재 C 백엔드의 구현이며 새 캠페인/의존성 모델에 연결할 대상이다.

## 대표 대상별 프로파일

| 대상 | 이전할 계약과 구조 | 검증 경로 |
|---|---|---|
| Linux 및 더 큰 시스템 소프트웨어 | 실제 C/C++ 빌드, ABI·메모리·장치·동시성·플랫폼, no_std 또는 사용자 공간 런타임 | 타깃 빌드, ABI/단위/통합 시험, 필요한 부팅·장치·성능 검사 |
| Ghidra와 복합 데스크톱/분석 도구 | Java/native 구성, 분석 코어·자료 모델·프로세서/파일 형식·스크립트/플러그인·UI, 외부 의존성 | 고정 바이너리 corpus의 분석 결과/metadata 비교, 플러그인·저장 프로젝트·CLI/UI 흐름 시험 |
| Spring Boot 애플리케이션 | 사용된 HTTP·DI·설정·DB·트랜잭션·보안·직렬화·lifecycle 계약 | 원본/Rust 서버의 HTTP 계약, DB 상태/rollback, 오류·인증/인가·설정/운영 흐름 비교 |
| Spring Boot 등 프레임워크 자체 | 프레임워크 기능/API와 런타임 모델, 의존 애플리케이션의 호환성 범위 | 대표 애플리케이션 corpus 및 기능별 호환 시험, 원본 API→Rust API 대응 |

Spring Boot 애플리케이션을 이전하는 것과 Spring Boot 프레임워크 자체를 Rust로 구현하는 것을 별도 작업으로 분류한다. 웹 프레임워크 후보 하나를 찾았다는 사실로 Spring의 DI, transaction, 설정, 보안 등의 호환성을 충족했다고 표시하지 않는다. Java API/바이트코드·플러그인 호환을 유지할지 Rust API로 이전할지도 계약에 명시한다.

Ghidra는 여러 분석 기능과 Java/Python 확장을 제공하는 도구이므로 특정 binary parser 후보 하나가 전체 제품을 대체한다고 간주하지 않는다. 아래 공식 자료는 대상의 구조를 이해하기 위한 근거이며 현재 포팅 성공의 근거가 아니다.

- [Spring Boot reference](https://docs.spring.io/spring-boot/reference/index.html)
- [Spring IoC container](https://docs.spring.io/spring-framework/reference/core/beans.html)
- [시스템/커널 전용 프로파일](kernel-scale-roadmap.md)

## 다음 기반 구현

1. **Migration campaign 및 인벤토리**: 여러 프로젝트/언어/빌드 생태계를 하나의 작업 그래프로 관리. CMake/Kbuild/compilation database, Maven/Gradle, Python/Go 등의 수집기를 교체 가능한 어댑터로 설계.
2. **공통 타입/동작 모델과 백엔드**: 기존 `Function.rust`에 결합된 분석과 생성을 분리. native, JVM 기반 앱, 서버/프레임워크를 각각의 런타임 계약과 출력 어댑터로 처리.
3. **의존성 티켓·후보·어댑터·검증 수명주기**: Agent가 검색해 얻은 후보를 조사 근거와 함께 제출하고, 실제 사용하는 API 범위의 계약 테스트와 연결. 맞는 후보가 없으면 의존 프로젝트 포팅으로 재귀적으로 연결.
4. **프로파일별 실행 worker와 자동 반복**: 빌드/원본 실행 환경, 검증 fixture, 후보/환경 fingerprint, 실패 진단, 예산과 checkpoint를 연결.

진행률은 원본 구현 이전, 라이브러리 직접 대체, adapter/reimplementation, FFI 잔여, unresolved dependency, 미검증 기능/설정의 분모를 유지해 보고한다. 원본 C/JVM에 위임한 기능이나 미실행 테스트를 Rust 구현 완료로 포함하지 않는다.
